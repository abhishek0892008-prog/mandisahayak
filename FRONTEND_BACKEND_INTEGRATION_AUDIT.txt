3. WHAT WAS BROKEN  —  and what each fix was
================================================================================

3.1  NO NETWORK LAYER AT ALL                                          [FIXED]
     There was no fetch, no axios, no client, no base URL, no error handling.
     FIX: src/lib/api.js - one client, credentials:'include', automatic CSRF
     echo, typed ApiError/NetworkError, 26 methods.

3.2  OTP ACCEPTED ANY SIX DIGITS                                      [FIXED]
     OTPVerification.handleVerify() set localStorage.isLoggedIn = "true" and
     navigated to the dashboard. It called nothing. Any six digits worked, and
     so did a booking made by someone who had never verified a phone.
     FIX: nothing proceeds without a 201 from POST /auth/otp/verify, which is
     the only thing that mints a session cookie. Expiry and resend cooldown are
     driven by the server's own expiresAt / resendAvailableAt timestamps.

3.3  LOGIN DISCARDED THE PHONE NUMBER                                 [FIXED]
     The login form had no state. The button navigated to /verify-otp without
     reading, validating or submitting the number.
     FIX: controlled input, validated, POST /auth/farmer/login/start-otp, and
     the returned challenge is carried to the OTP screen in router state.

3.4  REGISTRATION COLLECTED BANK ACCOUNT NUMBER AND IFSC              [FIXED]
     This was the most serious finding. The form collected a 9-18 digit bank
     account number and an IFSC code. The backend has NO COLUMN for either
     (decisions D-6/D-7), the endpoint ignores them, and README.md states
     publicly: "No Aadhaar and no bank details are collected anywhere."
     The form made that claim false, and wrote both to localStorage in plain
     text where any browser extension could read them.
     FIX: both fields removed entirely.

3.5  DISTRICTS WERE HARDCODED NAMES; THE API NEEDS UUIDs              [FIXED]
     Registration.jsx carried a literal list of five district names. The
     endpoint requires districtId as a UUID. Registration could never have
     succeeded.
     FIX: GET /reference/districts, and the id is submitted.

3.6  VILLAGES WERE 17 UNVERIFIED HARDCODED NAMES                      [FIXED]
     LGD village data was never retrievable; those names are invented.
     FIX: GET /reference/villages. When available:false the field is HIDDEN
     rather than rendered empty, and villageId is optional. The hardcoded list
     is gone and is not used as a fallback.

3.7  NO ROUTE PROTECTION                                              [FIXED]
     /dashboard, /profile, /queue, /payment were all reachable by typing the
     URL.
     FIX: ProtectedRoute + PublicOnlyRoute. Note this is a USABILITY control,
     not a security one - the server enforces every private endpoint. Its job
     is to stop a signed-out visitor landing on a screen that can only render
     errors. It renders a spinner while the session is unknown rather than
     redirecting, because the session cookie is HttpOnly and a cold load
     genuinely cannot know yet; redirecting early signed the farmer out on
     every refresh.

3.8  NO 404 ROUTE                                                     [FIXED]
     Any unknown path rendered a blank page.
     FIX: src/pages/NotFound.jsx, plus /register -> / redirect.

3.9  BOOKING INVENTED ITS OWN DATA                                    [FIXED]
     BookSlot.jsx had 3 hardcoded centre names, 4 fixed time slots with
     invented seat counts ("6 available"), and generated its own booking id in
     the browser. None of that survives contact with the real engine, where
     capacity is TIME ON A LANE sized to the quantity, the earliest fitting
     window is computed server-side under a row lock, and both the booking code
     and the token are minted by the server.
     FIX: the flow is now "describe what you are bringing -> ask the server what
     it can offer -> take it or not". The client proposes nothing.

3.10 QUANTITY WAS IN THE WRONG UNIT AND THE WRONG RANGE               [FIXED]
     <input min="1"> labelled kg. The real rule is 2500-5000 kg (25-50 quintal),
     the wire field is always quantityKg as an integer, and the range is also a
     PostgreSQL CHECK constraint.
     FIX: the UI collects quintal, converts with the server's own kgPerQuintal,
     and reads min/max from GET /reference/booking-constraints. The numbers are
     not hardcoded in the component, so the UI and the CHECK cannot drift apart.

3.11 QUEUE SCREEN WAS ENTIRELY FICTIONAL                              [FIXED]
     Token "FQ-0284", position 18, 17 farmers ahead, 35 minutes - all literals.
     FIX: GET /bookings/:code/queue. Both "ahead" numbers are shown, because one
     alone misleads: aheadOnLane predicts the wait, aheadAtCentre is what a
     farmer means by "how many are in front of me". The ETA always carries its
     etaConfidence (OBSERVED / PROJECTED / SCHEDULED / UNAVAILABLE), and when it
     is UNAVAILABLE the screen shows the reason instead of a number.

3.12 NOTIFICATIONS WERE SYNTHESISED IN THE BROWSER                    [FIXED]
     The list was generated from whatever booking happened to be in
     localStorage, so it could show an update about an event that never
     occurred.
     FIX: GET /notifications. Read state is a server write. The feed also
     carries the honest delivery note, because realSmsDelivered is false on
     every record in this build.

3.13 PROCUREMENT AND PAYMENT READ localStorage                        [FIXED]
     FIX: real endpoints. A 404 before arrival / before procurement is rendered
     as "not started yet", because that is a state, not a fault. The payment
     amount is taken from the server's exact decimal string, never re-derived
     from paise in JavaScript floating point.

3.14 LOGOUT WAS localStorage.removeItem                               [FIXED]
     FIX: POST /auth/logout revokes the session server-side.

3.15 CROP VOCABULARY DID NOT MATCH THE BACKEND        [FIXED — was P1-2]
     src/data/crops.js used ids "rice" and "mustard". The backend's canonical
     codes are PADDY and RAPESEED_MUSTARD, and crop ids are UUIDs.
     FIX: the file is now purely a SEARCH ALIAS TABLE keyed by the backend's 20
     canonical codes. It keeps the part the server does not provide and should
     not - the Hindi and romanised spellings a farmer actually types. The
     canonical name itself comes from the API and is deliberately never
     translated, because it is the government's own wording.

3.16 16 LINT PROBLEMS                                  [FIXED — was P2-2]
     All 14 errors were react-hooks/set-state-in-effect: every screen called a
     synchronous loadX() inside useEffect.
     FIX: structural, not cosmetic. src/hooks/useApiResource.js DERIVES the
     loading flag by comparing the settled request key against the current one,
     so no setState happens synchronously in an effect at all. The error class
     is now impossible to reintroduce through the normal data-fetching path.

3.17 ERROR MESSAGES WOULD HAVE BEEN UNTRANSLATABLE                    [FIXED]
     The contract is explicit: error.message is English developer text and must
     never be shown to a user; switch on error.code.
     FIX: src/lib/codes.js maps every server code to an i18n key. 261 keys were
     added to each bundle, covering every error code, field code, booking
     status, display status, queue state, ETA confidence and reason, payment
     status, blocked reason, quality status, procurement status, notification
     type and reason code. Both bundles are 441 keys and verified identical;
     a script confirms every t() key referenced in src/ exists.

5. THE OTP, AND HOW TO MOVE FORWARD QUICKLY
================================================================================

You asked to bypass the OTP or have the code shown. It is now SHOWN, using the
route the backend already provides for exactly this.

WHY NOT A BYPASS. A bypass would have to skip POST /auth/otp/verify, and that
endpoint is the only thing that creates the session cookie. Every screen behind
it - dashboard, booking, queue, payment - depends on that cookie. Skipping it
would not let you move forward; it would leave you signed out with a UI that
pretends otherwise, and it would delete the one acceptance criterion the whole
auth phase exists to satisfy.

WHAT HAPPENS INSTEAD. When the server runs with DEMO_MODE=true it keeps the
last OTP per phone IN MEMORY (never in the database - there is no plaintext OTP
column and this must not become one) and serves it from a token-protected,
fully audited GET /dev/last-otp. The OTP screen now calls that and shows the
code in an amber banner with a one-click "Fill this code" button.

The code is still submitted to /auth/otp/verify like any other. You get a real
session, so everything downstream genuinely works.

THIS CANNOT LEAK INTO PRODUCTION:
  - the server REFUSES TO START with DEMO_MODE and NODE_ENV=production together
  - DEMO_MODE requires DEV_TOOLS_TOKEN or the server refuses to start
  - the banner only renders when VITE_DEMO_OTP=true is set at build time
  - every reveal writes an audit row

TO USE IT
  server/.env      DEMO_MODE=true
                   DEV_TOOLS_TOKEN=local-demo-token
  .env.local       VITE_DEMO_OTP=true
                   VITE_DEV_OTP_TOKEN=local-demo-token      (must match)

The OTP is also printed in the server log on every request:
  {"level":"warn","msg":"DEMO_MODE OTP for ***22 (FARMER_REGISTER): 270275"}

6.3  server/package.json — THE ONLY BACKEND CHANGE
     The server reads process.env and nothing loaded server/.env, so `npm start`
     failed with "DATABASE_URL: Required" even with the file present. Two script
     lines now load it:
       start: node --env-file-if-exists=.env src/index.ts
       dev:   node --env-file-if-exists=.env --watch src/index.ts
     --env-file-if-exists (not --env-file) so the scripts still work when the
     environment is supplied another way, e.g. in CI.

     Also note the env var is SESSION_PEPPER, not SESSION_SECRET as
     server/.env.example suggests, and all three peppers need >= 16 characters.

6.4  FRONTEND
     cp .env.example .env.local
     npm install && npm run dev                      # http://127.0.0.1:5173

6.5  WHY THE VITE PROXY MATTERS - DO NOT "SIMPLIFY" THIS
     vite.config.js proxies /api to the backend so the browser sees ONE ORIGIN.
     This is not convenience. The session and CSRF cookies are SameSite=Lax and
     the backend deliberately ships NO CORS MIDDLEWARE. If you point
     VITE_API_BASE_URL at http://localhost:3000 directly, the cookies will not
     be sent and every authenticated request will 401.

     Keep VITE_API_BASE_URL=/api/v1. Change VITE_API_PROXY_TARGET instead.

6.6  RE-RUNNING THE BACKEND TESTS
     The suite books real windows against real lanes, so a SECOND run against
     the same database reports NO_AVAILABILITY - a stale database, not a
     regression. Always recreate first:

     TEST_DATABASE_URL=postgres://fqverify@127.0.0.1:55432/farmqueue_test \
       bash server/scripts/provision-database.sh --recreate

     This bit us during this very audit: the test database still held 368
     bookings and 0 notification templates from an earlier session, producing
     11 failing suites that had nothing to do with any code change. After a
     clean provision: 323/323 pass.

7. DESIGN DECISIONS THAT KEEP THIS FROM BREAKING
================================================================================

You asked for it to work "efficiently without breakdown". These are the choices
that matter, and the reasons, so they are not undone by accident.

7.1  ONE API CLIENT, NOT fetch() SCATTERED IN SCREENS
     CSRF handling, cookie mode, error shaping and query building exist once. A
     screen cannot forget to send credentials.

7.2  CSRF SELF-HEALS
     A write rejected with CSRF_TOKEN_INVALID re-primes the token and retries
     ONCE. Only that code is retryable and only once, so a genuinely forged
     request cannot loop. Without this a farmer whose cookie rotated would sit
     on a form that silently refuses to submit.

7.3  LOADING IS DERIVED, NEVER STORED
     useApiResource compares the settled request key with the current one. This
     is what eliminated all 14 lint errors structurally rather than by
     suppressing them, and it makes a stale response unable to overwrite a
     newer one.

7.4  EVERY REQUEST IS ABORTABLE
     An AbortController is torn down on unmount and on dependency change. Fast
     navigation cannot leave a late response writing into a dead component.

7.5  IDEMPOTENCY KEY PER PREPARED BOOKING
     Held in a ref, reused across retries of the SAME request, regenerated when
     the request changes. A double-tap replays the stored response instead of
     creating a second booking. On SLOT_NO_LONGER_AVAILABLE the offer is
     discarded and the key regenerated, because retrying against a window that
     no longer exists is meaningless.

7.6  POLL CADENCE COMES FROM THE SERVER
     QueueStatus adopts pollAfterSeconds from each response. Cadence is an
     operational decision; if the centre gets busy the server can slow every
     client down without a frontend release. Polling refreshes in the
     background and never returns the screen to a loading state, so a
     refreshing queue does not flicker.

7.7  THE UI COMPUTES NO BUSINESS VALUE
     Not position, not ETA, not the amount, not eligibility, not whether a
     transition is allowed. src/lib/format.js formats and returns null when
     given null - it never substitutes a placeholder number. Money uses the
     server's exact decimal string rather than dividing paise in floating point.

7.8  TIMES RENDER IN THE CENTRE'S ZONE
     Every window carries its own centreTimezone. A farmer must read the
     centre's clock, not the browser's.

7.9  ERRORS ARE CODES, NOT SENTENCES
     Nothing renders error.message. This is what keeps the app genuinely
     bilingual as the backend adds codes.

7.10 PROVENANCE IS SHOWN, NOT HIDDEN
     Wherever a CONFIGURED centre appears the UI labels it as demonstration
     data. The five centres correspond to no verified government facility and
     the UI must not let them look like one.

7.11 ONE LAYOUT, NOT TWELVE COPIES
     FarmerLayout owns the header and bottom nav. Previously each screen
     carried its own copy of both, which is exactly why the language toggle had
     already drifted between them.

9. HONEST REMAINING GAPS
================================================================================

  - No officer UI and no admin UI. Farmer app only.
  - No automated frontend tests. The verification in section 1 is a live HTTP
    journey, not a committed test suite. This is the largest remaining gap and
    the obvious next task.
  - The browser UI was verified by driving the same endpoints it calls and by
    confirming the dev server serves and proxies correctly. Each screen was not
    individually click-tested in a browser.
  - No real SMS. DEMO adapter only; realSmsDelivered is false everywhere.
  - No money moves. Payment status is tracked, never disbursed.
  - Notification preferences have a complete backend and no UI.
  - QUEUE_APPROACHING never fires - no threshold is configured anywhere, and
    inventing one is refused by design.
